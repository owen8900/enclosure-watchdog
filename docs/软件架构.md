# 软件架构

## 工具链

Keil MDK 或 STM32CubeIDE，配置由 STM32CubeMX 生成。

建议从 CubeMX 建工程，不要从厂商例程改起。厂商例程默认把程序放在外部
QSPI（0x90000000），改回片内 Flash 涉及链接脚本、启动文件和中断向量表
三处修改，比从零建一个干净工程麻烦。

## 工程配置

### 供电与电压等级

这颗芯片跑 480MHz 需要把内部稳压器设到 VOS0，但**不能直接设 VOS0**，
必须先切 VOS1、等稳压器稳定，再切 VOS0。顺序错了跑不到标称主频，
严重时直接起不来。

```c
HAL_PWREx_ConfigSupply(PWR_LDO_SUPPLY);
__HAL_PWR_VOLTAGESCALING_CONFIG(PWR_REGULATOR_VOLTAGE_SCALE1);
while (!__HAL_PWR_GET_FLAG(PWR_FLAG_VOSRDY)) {}
__HAL_RCC_SYSCFG_CLK_ENABLE();          /* 这步容易漏 */
__HAL_PWR_VOLTAGESCALING_CONFIG(PWR_REGULATOR_VOLTAGE_SCALE0);
while (!__HAL_PWR_GET_FLAG(PWR_FLAG_VOSRDY)) {}
```

供电模式用 LDO。板子是 LDO 供电，选 SMPS 会配错。

### 时钟

HSE 外部晶振 + PLL1，目标 SYSCLK 480MHz、HCLK 240MHz。

**主晶振频率需要看板子上的丝印确认后再填。** CubeMX 会根据填入值
自动计算 PLL 参数并标出不合规的组合。

### 调试口

`SYS → Debug` 选 `Serial Wire`，不能选 JTAG。原因见硬件设计文档。

### 时基

HAL 的时基要从 SysTick 换成 TIM6。FreeRTOS 会占用 SysTick，
两者冲突会导致 HAL 的延时和超时全部失准。

### 中断优先级

FreeRTOS 要求调用其 API 的中断优先级数值不低于 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`
（设为 5）。优先级分组用 `NVIC_PRIORITYGROUP_4`。
这一条违反了不会立刻报错，而是在某个时机偶发死机，很难查。

### 链接地址

保持 0x08000000（片内 128KB Flash），不要改成 0x90000000。
BOOT0 保持 0。这样才能用 ST-Link 直接下载，不需要 QSPI 下载算法。

## 任务划分

| 任务 | 优先级 | 周期 | 职责 |
|---|---|---|---|
| heater_ctrl | 7 | 10ms | 1Hz 时间比例控制，安全侧动作 |
| alarm_task | 6 | 100ms | 状态机推进、声光输出 |
| sensor_task | 5 | 100ms | 三路温度 + 电流电压采集 |
| net_task | 4 | 事件驱动 | Modbus TCP 从站、MQTT 上报 |
| ui_task | 3 | 50ms | 界面刷新 |
| storage_task | 2 | 事件驱动 | 环形日志落盘、断网续传 |
| diag_task | 5 | 100ms | 故障判据计算 |
| health_task | 1 | 1s | 栈水位统计、看门狗喂狗 |

优先级安排的依据：

`heater_ctrl` 最高，因为它的周期精度直接影响温控质量，
而且安全侧动作（切断输出）必须能立刻执行，不能被低优先级任务拖延。

`sensor_task` 和 `diag_task` 同优先级，都用 100ms 周期，
由 sensor 采完之后通过任务通知唤醒 diag。拆成两个任务是因为
采集要访问 I2C 总线，诊断是纯计算，分开之后诊断不会占着总线。

`health_task` 最低，它只在系统空闲时统计栈使用情况，
顺便喂狗。放在最低优先级可以保证：如果高优先级任务全部卡死，
喂狗也会停，看门狗能正常起作用。

## 任务间通信

任务之间只通过队列和任务通知传递数据，不共享全局可变变量。

```
sensor_task ──[队列 sensor_q]──> diag_task
diag_task   ──[队列 event_q ]──> alarm_task / net_task / storage_task
```

队列深度 8，元素是定长结构体。初始化之后不再动态分配内存，
所有队列和缓冲区都是静态分配。

## 共享总线保护

SPI1 上挂了 TFT、触摸、W5500 三个从机，是全工程唯一的共享资源。

```c
if (xSemaphoreTake(spi1_mutex, pdMS_TO_TICKS(50)) == pdTRUE) {
    /* 访问总线 */
    xSemaphoreGive(spi1_mutex);
} else {
    /* 取锁超时：记录，跳过本次访问 */
}
```

**取锁必须带超时。** 用 `portMAX_DELAY` 等待，一旦某个任务在持锁期间
出问题，其余两个会永久阻塞，形成死锁。超时之后宁可丢一帧显示，
也不能让系统卡死。

I2C1 同样处理。SPI 的 DMA 传输还需要注意 Cache 一致性，
见下面一节。

## H7 的 Cache 一致性

H7 有 D-Cache 且默认开启。用 DMA 传输时，CPU 写的数据可能还在 Cache 里
没落到内存，DMA 读到的是旧值；反过来 DMA 写进内存的数据，
CPU 读的时候可能读到 Cache 里的旧副本。

发送前清理，接收后失效：

```c
SCB_CleanDCache_by_Addr((uint32_t *)buf, len);      /* 发之前 */
SCB_InvalidateDCache_by_Addr((uint32_t *)buf, len); /* 收之后 */
```

另一个办法是把 DMA 缓冲区放在 MPU 配置为 non-cacheable 的区域。
正点原子的例程里是把 0x60000000（FMC）和 0x80000000（NAND）设成
non-cacheable，本项目用 SPI 屏不涉及 FMC，暂时不需要配 MPU，
但一旦启用 SPI+DMA 就必须处理这个问题。

## 模块接口

`code/App/` 下的模块都不依赖硬件头文件，硬件相关的部分用函数指针注入：

```c
/* 加热控制：PWM 输出由外部注入 */
typedef void (*pwm_set_fn)(uint16_t duty);
void heater_init(pwm_set_fn fn);

/* 数据记录：文件读写由外部注入 */
void recorder_init(read_fn r, write_fn w);
```

这样同一份代码既能在 PC 上跑验证用例，也能直接编进固件，
不需要套 `#ifdef` 或者维护两份。

## 开发顺序

自底向上，每层通过验证再往上走：

1. 硬件抽象层：GPIO、SPI、I2C、UART、延时、printf 重定向
2. 外设驱动层：ILI9341、SHT30、DS18B20、INA219、W5500、TF 卡
3. 实时系统层：FreeRTOS 移植、队列、互斥量、看门狗
4. 应用逻辑层：采集调度、告警状态机、故障诊断、加热控制
5. 通信展示层：Modbus TCP 从站、MQTT 客户端、界面、日志存储
6. 验证层：外设单独测试、集成测试、故障注入、72 小时压力测试

其中第 4 层是唯一可以完全脱离硬件开发的，已经先做完了。
第 1 到 3 层必须上板才能进行。

## 调试注意

ST-Link 连 H7 时常报 `Target not responding`，原因是芯片默认处于
低功耗状态，调试器连不上内核。把调试配置里的 Reset 模式改成
`Connect under reset` 即可，不是硬件故障。
